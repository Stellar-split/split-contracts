# Issue #1113: Modular contract refactor (status)

**Status:** not done. No code is moved. This note gives the measured starting point, corrects a claim in the
existing plan, and lays out the first steps in an order that can be reviewed one at a time. The plan itself is
[`ISSUE_966_LIB_MODULE_PLAN.md`](./ISSUE_966_LIB_MODULE_PLAN.md).

## Why no code moved here

`contracts/split/src/lib.rs` is 20,020 lines with 11 `#[contractimpl]` blocks. Moving a group of functions is a
mechanical edit, but a wrong visibility or a missed import fails the build, and the rules for this run do not
allow building or testing. A refactor that was not compiled would risk breaking the contract for the
maintainers, so the work is split into steps that each can be built and tested on their own.

## A correction to the existing plan

`ISSUE_966_LIB_MODULE_PLAN.md` says `#[contractimpl]` requires every public function in one impl block. That
is not the case in this repository. `lib.rs` already has 11 blocks, and four modules define their own:
`insurance_pool.rs`, `sustainability.rs`, `cooperative.rs` and `education_lockup.rs` each start with

```rust
use crate::SplitContract;
#[allow(unused_imports)]
use crate::{SplitContractArgs, SplitContractClient};

#[contractimpl]
impl SplitContract { /* ... */ }
```

So a group of functions can move to a module as its own `#[contractimpl] impl SplitContract` block, with no
delegating method per function. The public interface, the generated client and the function names stay as they
are. The risks that remain are the ones in the plan: helper visibility and the instruction budget.

## First candidates

These are already separate blocks or have a single clear owner, so they are the lowest risk. Order is from the
smallest and most self-contained:

1. **Blocks 3 to 11** (about 1,500 lines). Each block is one issue with its own comment header, for example
   "Issue #1034: Contract usage analytics" and "Issue #929: Reversible operations". They move one block per
   commit into the module of the same name where one exists (`analytics`, `monitoring`,
   `payment_tracking`, `velocity`, `split_rules`, `security_audit`), and into new `archival`, `recipient_auth`
   and `reversal` modules otherwise.
2. **Block 2** (about 1,070 lines). Its sections are labeled by issue (#930 webhooks, #437 payout delay, #438
   anonymity, #431 duplicate detection, #432 referrals, #434 groups, #475 multi-sig admin, #560 creator
   migration, #562 soft delete, #476 templates). `webhooks` already exists, so #930 goes there first.
3. **Block 1** by its section headers. The ones with a clear boundary are the circuit breaker (#297 / #923),
   fee waivers (#296 / #922), compute estimation (#298, #316, #924), the upgrade timelock and freeze (#310, #435),
   confidential amounts (#295), dispute and arbitration (#188, #325) and the payment delegation (#315).
4. **The helper functions** (lines 145 to 3,638) move last. Many are used by several groups, so they should go
   to a shared module only after the groups that use them have moved, and be made `pub(crate)` as needed.

## Procedure for each step

1. Cut one block and paste it into the target module with the header above.
2. Add `use crate::*`-style imports for the helpers it calls, and make each helper it needs `pub(crate)`.
3. Build, then run `cargo test --workspace`. The tests in `test.rs` call the generated client, so they must
   pass without edits.
4. Compare the generated function list before and after. The contract spec must not change.
5. Check the instruction budget with the figures in `COMPUTE_BUDGETS.md`, since moving code can change inlining.
6. One module per commit, so a regression can be traced to one move.
