# Partial-refund and pause-all coverage, payment variance tolerance, recipient veto

**Stacked on #842 - please merge #842 first.** #799 / #802 describe the same features as #801 / #800, which #842 implements (`partial_refund` deadline / fully-funded guards; `pause_all_invoices` / `resume_all_invoices`). This branch starts from #842's head and adds the complementary pieces #842 left undone, so the two PRs don't conflict. Until #842 merges, this PR's diff also shows #842's commits; the commits specific to this PR are the last five.

Each issue gets its core piece plus tests in `contracts/split/src/test.rs`. The remaining requirements are listed under "Not done in this PR".

## #799 - refundPartial

On `main` + #842: `partial_refund(creator, invoice_id, bps)` refunds `bps / 10_000` of each payment, emits `payer_refunded` (`pay_ref`) per payer and `partial_refund_issued` (`prt_ref`) once, and (#842) is rejected after the deadline or on a fully funded invoice.

**Done**
- `test_799_partial_refund_emits_events_and_allows_further_payments`: one `pay_ref` per payer plus one `prt_ref`; the invoice stays `Pending` with `funded` reduced; a refunded payer can pay again and `funded` / balances add up.

**Not done in this PR**
- Separately named `RefundInitiated` / `RefundProcessed` events (the existing `prt_ref` / `pay_ref` events carry the same information).

## #802 - pause_all_invoices

**Done**
- Tests that `pause_all_invoices` also blocks `release` and `refund` (#842 covered `pay`), and that `resume_all_invoices` re-enables `refund`.

**Not done in this PR**
- A typed `InvoiceSystemPausedError`: the shared "contract is paused" panic is asserted by many existing tests.

## #805 - payment variance tolerance

**Done**
- `set_payment_variance(creator, invoice_id, variance_bps)` - creator-only, while Pending, max 1000 bps ("variance exceeds 1000 bps"). A setter rather than an `InvoiceOptions` field because that struct is at the 40-field `#[contracttype]` limit.
- The main `pay` path treats `funded >= target * (1 - variance)` as fully funded (normal guards still apply) and emits `FullyFundedWithVariance` (`split`, `var_fund`, invoice_id; data = (funded, target)). `_release_full` already splits the funded amount proportionally, so a short release pays out exactly what was collected.
- Tests: 5% variance, 950 of 1000 paid -> released, recipient receives 950, event emitted; 949 -> stays Pending, no event; 1001 bps rejected.

**Not done in this PR**
- Upper bound of the range (overpayment is governed by the existing overflow policy).
- Variance on the alternate payment paths (`pay` with alternate token, batch pay, etc.).
- `payment_variance_bps` in `InvoiceOptions`.

## #806 - recipient veto

**Done**
- `veto_release(recipient, invoice_id)` (listed recipients only, while Pending), `clear_veto(recipient, invoice_id)`, `get_release_vetoes(invoice_id)`; events `veto` / `veto_clr`.
- `release_invoice` panics with "VetoBlocked" while any veto stands; the main `pay` path holds funds instead of auto-releasing while vetoed.
- Tests: veto blocks release; clearing it re-enables release; a vetoed invoice is not auto-released on full funding; a non-recipient can't veto.

**Not done in this PR**
- A designated `veto_recipients` list in `InvoiceOptions` (every recipient can veto for now).
- A typed `VetoBlocked` error, and veto checks on `trigger_scheduled_release` / other release paths.
